# Jal Mitra 360 (ஜல் மித்ரா 360)
### AI-Based Self-Learning & Self-Maintaining Rural Water Monitoring System with Adaptive Response

Jal Mitra 360 is a full-stack IoT and AI-driven rural water distribution management platform built for Gram Panchayats and Rural Water Supply engineers.

---

## 🚀 Quick Start Guide

### Prerequisites
- Node.js 18+ or 20+
- npm or bun

### 1. Installation
```bash
npm install
```

### 2. Run the Development Server
```bash
npm run dev
```
Open your browser at `http://localhost:3000`.

### 3. Build for Production
```bash
npm run build
npm start
```

## ✨ Key Features & Highlights

1. **Role-Based Access Control (RBAC)**:
   - Separate logins for **Villagers (கிராம மக்கள்)**, **Panchayat Admins (ஊராட்சி நிர்வாகி)**, and **Technical Supervisors (தொழில்நுட்ப மேற்பார்வையாளர்)**.
2. **Automated 5-Day SLA Escalation Workflow**:
   - Village water complaints unresolved within **5 days** trigger immediate, critical escalation notifications dispatched directly to Technical Supervisors.
   - Dedicated filter and visual badge in the Complaints register (`>5 Days Overdue SLA`).
3. **Sensor Health & Live Diagnostics (`/sensors`)**:
   - Live telemetry monitors for Ultrasonic Water Level, Turbidity NTU, Pipeline Pressure, Flow meters, and Free Residual Chlorine.
   - Signal-to-Noise Ratio (SNR), baseline drift calculation, and zero-point recalibration.
4. **Self-Maintaining Sensor Wiper Simulation (`/self-maintaining`)**:
   - Interactive 5-stage mechanical actuation simulation (Bio-film detection $\rightarrow$ acoustic SNR analysis $\rightarrow$ actuator wiper sweep $\rightarrow$ re-measurement $\rightarrow$ validation & restoration).
5. **Multi-Language Support**:
   - Full toggle between English and Tamil (தமிழ்).
6. **ESP32 IoT Ingestion API**:
   - `/api/esp32/telemetry` for live IoT sensor ingestion.
   - `/api/ai/analyze` for pipeline burst and transducer fouling predictive heuristics.

## Apache Spark + Scala Water Analysis

`WaterAnalysis.scala` is a real Apache Spark SQL batch-processing job. It reads the JAL MITRA 360 water-network CSV using an explicit schema, cleans and enriches the DataFrame, prints nine review-ready analyses, and writes CSV review directories plus API-ready JSON directories under `output/` (or the output path supplied on the command line).

### Prerequisites and Run

- JDK 8, 11, or 17
- Scala 2.12.18 and sbt 1.9+
- Apache Spark 3.5.1 installed so `spark-submit` is available
- A CSV containing the documented water-network columns, with a header row

From the repository root, package and run the job:

```bash
sbt package
spark-submit --class WaterAnalysis --master 'local[*]' \
   target/scala-2.12/jalmitra-water-analysis_2.12-0.1.0.jar \
   data/water_network.csv output
```

Replace `data/water_network.csv` with the path to the real dataset. No sample telemetry is generated by the program. The output contains:

- `output/village_average_water_level/`
- `output/village_average_flow/`
- `output/tank_water_usage/`
- `output/leakage_risk_records/`
- `output/abnormal_sensor_readings/`
- `output/pump_status_summary/`
- `output/village_water_wastage/`
- `output/village_complaint_summary/`
- `output/overall_water_supply_summary/`
- `output/api/village_average_water_level/`
- `output/api/village_average_flow/`
- `output/api/tank_water_usage/`
- `output/api/leakage_risk_records/`
- `output/api/abnormal_sensor_readings/`
- `output/api/pump_status_summary/`
- `output/api/village_water_wastage/`
- `output/api/village_complaint_summary/`
- `output/api/overall_water_supply_summary/`

Spark writes a directory per CSV/JSON result, typically with one or more `part-*` files and a `_SUCCESS` marker. This is normal Spark output, not a single file. Aggregated usage and complaint totals describe the entire time period present in the input file; avoid summing repeated cumulative snapshots if the source data stores running totals rather than per-record amounts.

### What the Job Demonstrates

- **SparkSession:** creates the entry point for Spark SQL and DataFrame work.
- **CSV loading and inspection:** reads with a declared schema, prints the schema, shows sample records, and counts rows.
- **Cleaning:** trims text columns, removes records without record/village IDs, removes duplicate `Record_ID` values, and rejects negative physical measurements while preserving null measurements.
- **Transformations:** `withColumn`, `filter`, `dropDuplicates`, `select`, `groupBy`, `agg`, and `orderBy` build new DataFrames. Transformations are lazy until an action needs a result.
- **Actions:** `show`, `count`, and CSV `write` execute the DataFrame plan and produce visible or persisted results.
- **Feature engineering:** calculates flow difference, supply-efficiency percentage, leakage-risk band, and abnormal-sensor reason.

### Analysis Tables

1. Average water level by village
2. Average inlet/outlet flow by village
3. Tank-wise demand, supplied water, wastage, and average level
4. Records with a reported leak or leakage risk of at least 60%
5. Abnormal sensor status or physically out-of-range readings
6. Pump status, average runtime, and energy consumption
7. Total and average wastage by village
8. Complaint totals by village
9. One-row overall supply/network summary

### Where Spark Fits in JAL MITRA 360

The React application and Express server handle interactive screens, login, current alerts, and request/response APIs. Spark belongs in the data-processing layer: it can batch-process historical ESP32 telemetry and complaint/supply records from CSV, a data lake, or a database, then produce network-wide operational summaries that are too large or costly to recompute in each browser session.

Scala is used because it is Spark's native JVM language, has typed APIs and compile-time checks, and integrates directly with Spark SQL. Spark is suitable for sensor data because it distributes CSV/parquet processing and aggregations across cores or machines, and the same DataFrame code can scale from local review-sized data to a cluster.

### Spark Results in the Website

Spark runs as a batch job, not inside a React browser. The Scala job writes JSON Lines under `output/api/`; Express serves those generated files from `GET /api/spark/analytics`; the admin sidebar's **Spark Analytics** page fetches that endpoint and displays KPIs plus selectable tables for all nine results. The page includes loading, error, refresh, and not-yet-generated states and shows only actual Spark output.

Run the Spark job from the repository root so `output/api/` matches the API's default directory. If it writes elsewhere, set `SPARK_OUTPUT_DIR` to the generated `api` subfolder before starting the Node server. Once the Spark batch finishes, open Spark Analytics and press refresh.

Data flow: telemetry CSV -> Scala/Spark batch job -> CSV review files + JSON summaries -> Express `/api/spark/analytics` -> React Spark Analytics page.
